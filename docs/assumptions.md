# Working assumptions

These are the assumptions the implementation makes where the DTG and VTI working groups
haven't decided yet. The code names each one as `A<n>`. When the WG decides, change the code
at the places listed for that assumption.

WG threads:
- [dtgwg-cred-spec discussion #82](https://github.com/trustoverip/dtgwg-cred-spec/discussions/82)
- [PR #83](https://github.com/trustoverip/dtgwg-cred-spec/pull/83)

| # | Assumption | Open question | Where |
|---|---|---|---|
| A1 | **A listing is a VSC**, under the registered predicate `https://registry.trustoverip.org/dtg/vsc/lists/1`, with `object.value` = `{ nodeType: VTC\|VTN, framework }`. It is not an unacknowledged VMC grant. *Partly resolved:* the WG agreed this on #82, and dtgwg-vsc-registry #33 registered `lists/1` and `repudiates/1`. The group profiles (`servesRole`, `groupRegistered`) still live in the OpenVTC namespace `https://openvtc.org/vtn/vsc/` until they are registered. | #82 item 3 | `vti-vtn/src/vocab.rs`, `credentials::listing_vsc` |
| A2 | **Membership is offered unsigned.** The network publishes the VMC grant's claims without a proof. The party signs an acknowledgement over their digest, and the network signs the grant only after that. The digest excludes `proof`, so the acknowledgement matches the signed grant. This satisfies both DTG Core (grant before acknowledgement, digest-bound) and VTI-VTN-013 (no membership credential before the party agrees). | #82 item 3 | `credentials::membership_offer`, `Network::acknowledge` |
| A3 | **A VTN's members may be VTCs or VTNs.** The VMC subject can be either. | PR #83 item 1 | used throughout; entries carry `kind` |
| A4 | **The member's acknowledgement declares `issuerScope: public`.** If no `validUntil` is given, it defaults to the grant's. The network does not hold the acknowledgement's status, so the graph marks it `unchecked`. | PR #83 item 5, issue #75 | `credentials::member::acknowledge`, `graph::export` |
| A5 | **The identity is VTA-provisioned (done).** `vtn setup` asks the VTA to mint the network's `did:webvh` from the `vtn-host` template (`templates/vtn-host.json`), registered in the context. The service keeps the VTA-minted keys in a `vti-secrets` store and signs with the Ed25519 key, `#key-0`. Parties are resolved through the VTA SDK's purpose-checking resolver (VTI-KEY-022). The remaining assumptions: <ul><li>The template is operator-registered rather than a VTA built-in.</li><li>Only the Ed25519 key signs. A post-quantum second proof, as the VTC does, comes later.</li><li>`vtn init` keeps a development `did:key` with no VTA.</li></ul> | — | `vtn-service/src/{setup,identity}.rs` |
| A6 | **Admins are DIDs** listed in `admins` in `vtn.toml`. Each request an admin sends is a Trust Task they sign for `authentication`; there are no sessions. This is what the NNM does. Keys an admin delegates (`auth/signing-key/*`) are still to come, as are VTI roles (owner, curator, broadcaster, auditor) and approvals/step-up (VTI-VTN-004/005) are still to come. | — | `vtn-service/src/auth.rs` |
| A7 | **Status lists:** each issued credential gets one index, used in both the `revocation` and the `suspension` Bitstring Status List. The VTN serves both lists itself. | — | `vti-vtn/src/status.rs` |
| A8 | **Repudiation semantics:** <ul><li>Repudiating the listing makes the entry `repudiated`. The listing stays published next to the repudiation, and the pending offer is revoked.</li><li>Repudiating the grant makes the entry `departed`. Everything the network issued for it is revoked.</li><li>The network may list a party again after it repudiates. The old listing is revoked. Whether that is allowed is a governance-framework question.</li></ul> | VTI-VTN-012 | `lifecycle.rs`, `Network::repudiate`, `Network::list` |
| A9 | ~~**REST only.**~~ *Superseded:* the API is Trust Tasks (`vtn/*/0.1`, trustoverip/dtgwg-trust-tasks-tf#1020; contract in `docs/trust-tasks.md`). REST stays only for the landing page, `/.well-known/vtn`, status lists, the signed index, credential fetch and the `/health` probes. | — | `tasks/`, `routes.rs` |
| A10 | **This is a standalone workspace.** It depends on the published `vti-common` for its store. It does not wait for the `vti-community-core` extraction (design phase 0). | — | `Cargo.toml` |
| A11 | **The NNM keeps the admin key in its profile file** (`~/.nnm/profile.json`, 0600). PNM and CNM use the OS keyring or a VTA. The admin DID can be a `did:key` the NNM generates, or a VTA-minted DID imported with `nnm keys import`. | — | `nnm-cli/src/profile.rs` |
| A12 | **Resolved.** A person's membership credential is checked against the issuing community's status lists whenever it is presented. Each list is verified as signed by the community. An unreachable list is refused as indeterminate. | — | `Network::verify_member_credential`, `vti_vtn::StatusChecker` |
| A13 | ~~**Browser sign-in uses a VTN-specific link.**~~ *Superseded by Trust Tasks:* the landing page's own Ed25519 key is approved by a wallet through `auth/oob/*` (`vti-oob-server`, shared with the VTC). `redeem` delegates the key to the approver for the reads in `tasks::oob::SIGNING_SCOPE` until the earlier of the grant's end and `[auth] browser_key_hours` (8 by default, at most 24, A20); there is no session or cookie. An administrator or a listed or member community or network may approve, decided from local records before the DID is resolved (T15). A person holding a member community's credential cannot sign in this way, as the network has no record of them; they present the credential with each request. Keys an administrator delegates (`auth/signing-key/*`) are still to come. | — | `tasks/oob.rs`, `web/index.html` |
| A14 | **A network group is a DID URL on the network's DID:** `<network DID>#role-<name>`. It is not a DID of its own minted by the VTA, as the design (§5) has it. `servesRole` is retired: the member's signed `vtn/groups/register` request replaces it. The network's acceptance stays a revocable `groupRegistered/1` VSC in the OpenVTC namespace (A1), binding that request by digest. | design §5, open question 2 | `vti_vtn::groups` |
| A15 | **Broadcast delivery is HTTPS, with a durable retry queue.** A delivery that fails in transport is stored in the outbox and retried with exponential backoff (`relay.retry_base_seconds`, doubling, capped at an hour). Retries stop when the delivery succeeds, the message expires, or `relay.max_attempts` is reached. Refusals are final. Each network queues its own deliveries, and receipts already returned up the chain are not revised by a later downstream retry. Delivery to a member network's group is a `vtn/relay/deliver` Trust Task signed by this network, to the endpoint it registered (its `/v1/trust-tasks`); the deliverer must be a network the receiver joined, and the envelope's last hop must be the deliverer's. A community's group endpoint is still any HTTPS URL that accepts `{ envelope }`, until `vtc/networks` 0.2. TSP/DIDComm delivery is still to come. | design §5.3 | `vtn-service/src/broadcast.rs` |
| A16 | **Federated search reaches a member network at its entry profile's `url`**, set by the parent's admins. It does not resolve the member's DID document `VerifiableTrustNetwork` service. Member indexes are fetched signed, verified against the member's DID, and cached for five minutes. A member network whose index is restricted or unreachable is reported as indeterminate. | design §7 | `vtn-service/src/federation.rs` |
| A17 | **The network issues room passes; a room host hosts the room.** A pass is a VAC (`room:enter`, scope `<network DID>#room-<id>`, short `validUntil`) issued on a chain of evidence the person presents: their group's membership credential, plus a signed `vtn/groups/register` request and its `groupRegistered` acceptance per network level. They ask with `vtn/rooms/pass`, signed by themselves, so the signer is the holder. Each item is verified for signature and status, and the chain must end at a group registered here, for the room's role, by a current member. The person's community hands them the chain links. A room host (`vti-rooms` / `room-host`, room owned by the network DID) is expected to honour the pass. | design §5.4 | `vti-vtn/src/rooms.rs`, `vtn-service/src/rooms.rs` |
| A18 | **Fetched status lists are trusted for `status_cache_seconds`** (default 300) before refetching, so a revocation at a community or member network can take that long to take effect here. | VTI-REG-011 | `vti_vtn::StatusChecker` |
| A19 | **Trust Tasks are the API; credentials are the proof.** No Trust Task document evidences a relationship. Listing, membership, repudiation, group acceptance, a person's membership and room passes are all DTG credentials, checkable later against keys and status lists. | — | `docs/trust-tasks.md` |
| A20 | **Short lifetimes for anything not revocable.** Requests are accepted within 10 minutes of `issuedAt`. Browser and delegated keys last at most 24 hours (8 by default). Room passes last at most 24 hours (60 minutes by default). Broadcasts last at most 7 days (24 hours by default). | — | `docs/trust-tasks.md` |
| A21 | **The index and credentials are fetched unsigned, so only a public directory serves them.** VTI's `Trust-Task` header carries a task's Type URI, not a signed document, so there is no convention yet for an authenticated `GET`. In a restricted network the same credentials are read through `vtn/entries/show` and `vtn/graph/show`, which carry the reader's signature, and a parent's federated search reports a restricted member network as indeterminate (A16). | `docs/trust-tasks.md` | `routes.rs` |
| A22 | **Repeating a transition is answered, not refused.** The same acknowledgement or repudiation again returns the entry as it stands; suspending a suspended entry, reinstating an acknowledged one and removing a removed one change nothing. `listings/update` changes only the fields named, and an empty string clears one. A group already registered here by another member is `groupTaken`. | — | `tasks/mod.rs`, `groups.rs` |
